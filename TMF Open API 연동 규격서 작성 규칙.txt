# TMF Open API 공통 연동 규격서 작성 표준 및 AI 작성 가이드

## 1. 목적 및 적용 범위

### 1.1 목적

TM Forum Open API의 공식 표준을 기반으로 API별 기능, 데이터 모델, 인터페이스, 상태 전이 및 이벤트 규격을 일관된 형식으로 분석·작성하여 연동 규격서의 완전성, 정확성 및 추적성을 확보한다.

### 1.2 적용 범위

- **적용 대상:** TM Forum Open API 전체
- **적용 API 예시:** TMF620 Product Catalog, TMF622 Product Order, TMF632 Party, TMF679 Product Offering Qualification, TMF701 Process Management 등
- **적용 버전:** 분석 대상 API의 공식 버전별 명세
- **분석 대상:** API 개요, Operation, Resource, 데이터 모델 및 하위 모델, 요청·응답, 파라미터, 상태 전이, 이벤트·알림, 오류 응답 및 관련 표준
- **작성 언어:** 한국어
- **표준 용어:** TMF 공식 API명, Resource명, 속성명, Operation ID, Enum 값 및 URI는 원문 표기를 유지하고 설명을 한국어로 작성한다.

본 표준은 공통 작성 규칙을 정의한다. 개별 API에 실제로 존재하지 않는 Resource, Operation, 상태, 이벤트 및 속성을 의무적으로 만들어 넣는 것은 금지한다.

## 2. 공통 작성 원칙

| 구분 | 작성 원칙 |
|---|---|
| 공식 표준 우선 | 대상 API 버전의 공식 OAS/Swagger를 기본 근거로 사용하고 User Guide, Conformance Profile 및 공식 예제를 보조 자료로 활용한다. |
| 버전 일치 | 분석 대상 API 버전과 근거 문서의 버전을 확인하고, 다른 버전의 정의를 혼합하지 않는다. |
| 원문 보존 | API ID, API명, Resource명, 속성명, HTTP Method, Endpoint, Operation ID, Enum 값 및 표준 코드값은 임의로 번역하거나 변경하지 않는다. |
| 전체 항목 분석 | 대표 항목만 선별하지 않고 대상 명세에 정의된 모든 Operation, 데이터 모델 및 속성을 분석한다. |
| 하위 모델 추적 | `$ref`, 배열의 `items`, 중첩 객체 및 상속·조합 구조를 추적하여 참조되는 하위 모델을 분석한다. |
| 근거 기반 작성 | 명세에 정의된 내용과 분석자가 해석한 내용을 구분한다. 근거가 없는 사항은 추정으로 확정하지 않는다. |
| 예시 구분 | 공식 예제와 분석 편의를 위한 가상 예시를 구분하여 표시한다. |
| 조건부 항목 적용 | 상태 전이, 이벤트, Hub, Callback, 인증·권한 등은 대상 API 명세에 존재하거나 공식 자료로 확인되는 경우에 작성한다. |
| 추적성 확보 | 주요 분석 결과는 출처 문서, 버전, Schema, Operation 또는 관련 섹션과 연결한다. |
| 검증 가능성 | 분석 결과를 원본 명세와 대조할 수 있도록 항목 수, 누락 여부, 미확인 사항을 점검한다. |

## 3. 분석 자료 및 근거 관리

### 3.1 자료 우선순위

1. 대상 버전의 공식 OpenAPI Specification(OAS)/Swagger
2. 동일 버전의 공식 TM Forum User Guide
3. 동일 버전의 공식 Conformance Profile
4. 공식 JSON 예제, Postman Collection 및 관련 공식 자료
5. 사용자가 제공한 추가 자료
6. 분석자의 해석 또는 별도 조사 결과

자료 간 불일치가 발생하면 임의로 통합하지 않는다. 버전 차이와 정의 차이를 기록하고, 공식 근거를 기준으로 판단하거나 검토 필요 사항으로 분류한다.

### 3.2 근거 기록 규칙

| 항목 | 작성 내용 |
|---|---|
| 근거 자료명 | 공식 문서 또는 제공 자료의 파일명 |
| API ID / API명 | TMF 표준 식별자와 공식 명칭 |
| API 버전 | 분석 대상 버전 |
| 근거 위치 | Schema명, Operation ID, Endpoint, 섹션 또는 예제 위치 |
| 확인 결과 | 확인된 사실과 적용 내용 |
| 검증 상태 | 확정 / 검토 필요 / 근거 미확인 |
| 비고 | 자료 간 차이, 해석 기준 및 추가 확인 사항 |

공식 자료를 확보하지 못한 경우 해당 자료를 분석한 것처럼 기술하지 않는다.

## 4. 공통 연동 규격서 목차

### 1. API 개요

- API ID 및 공식 API명
- API 버전 및 표준 문서 정보
- API 목적과 주요 기능
- 적용 업무 및 주요 사용 시나리오
- API 성격 및 제공 기능
- 관련 TM Forum 표준 및 연관 API
- 분석 대상과 제외 범위

### 2. 기능 및 Operation 요약

대상 OAS에 정의된 Operation을 전수 조사한다.

| HTTP Method | Endpoint | Operation ID | 기능 설명 | 주요 Resource | 비고 |
|---|---|---|---|---|---|
| OAS 정의값 | OAS 정의값 | OAS 정의값 | 한국어 설명 | 관련 Resource | 조건 및 참고사항 |

- GET, POST, PATCH, DELETE 등 실제 정의된 Method를 작성한다.
- Endpoint와 Operation ID를 원문 기준으로 유지한다.
- 목록 조회, 단건 조회, 생성, 수정, 삭제, 이벤트 구독 등의 기능을 명세에 따라 구분한다.
- 지원하지 않는 기능을 일반적인 REST API 관행만으로 추가하지 않는다.

### 3. Resource 및 데이터 모델 구조

- 주요 Resource와 Schema 목록
- Resource 간 참조 관계
- 데이터 모델 계층 구조
- 상위·하위 모델 관계
- 공통 모델 및 확장 모델
- 모델 간 관계 및 참조 방식

가능한 경우 다음 구조로 모델 관계를 표현한다.

`주요 Resource → 주요 Schema → 하위 Schema → 중첩 객체·배열 모델`

모델 간 관계는 실제 명세의 `$ref`, `allOf`, `oneOf`, `anyOf`, 객체 속성 및 배열 정의를 근거로 작성한다.

### 4. 데이터 모델별 전체 속성 명세

**모든 Schema와 하위 데이터 모델을 대상으로 모든 속성을 빠짐없이 작성한다.**

#### 4.1 필수 컬럼 순서

| 속성 | 타입 | 예시 | 설명 |
|---|---|---|---|
| OAS 속성명 | OAS 타입 및 제약조건 | 공식 예제 또는 가상 예시 | 속성의 의미와 사용 조건 |

위 4개 컬럼의 순서를 공통 기본 형식으로 적용한다. 필수 여부, 기본값, 허용값, 제약조건 및 출처 등 추가 정보가 필요한 경우 별도 컬럼 또는 보충 설명으로 제공한다.

#### 4.2 속성 작성 규칙

1. Schema에 정의된 모든 속성을 작성한다.
2. 중첩 객체의 하위 속성까지 재귀적으로 분석한다.
3. 배열은 배열 자체의 타입과 `items`에 정의된 원소 모델을 모두 설명한다.
4. `$ref`로 참조된 모델은 실제 Schema를 찾아 별도 항목으로 작성한다.
5. 상속·조합 구조인 `allOf`, `oneOf`, `anyOf`는 각 참조 모델과 적용 관계를 설명한다.
6. `required`에 정의된 필수 속성은 필수 여부를 별도로 표시한다.
7. `enum`, `const`, `default`, `format`, `pattern`, `minimum`, `maximum`, `minLength`, `maxLength` 등 정의된 제약조건을 누락하지 않는다.
8. `nullable`, 읽기 전용·쓰기 전용 속성, 다형성 관련 정의가 있으면 해당 명세를 확인해 설명한다.
9. 공통 속성인 `id`, `href`, `@type`, `@baseType`, `@schemaLocation` 등은 해당 모델에 실제로 정의되거나 상속·참조를 통해 적용되는 경우에만 작성한다.
10. 속성 설명이 공식 명세에 없는 경우 임의로 공식 설명처럼 작성하지 않고 `공식 설명 미확인` 등으로 표시한다.

#### 4.3 타입 표기 규칙

| 유형 | 작성 방법 |
|---|---|
| 기본 타입 | string, integer, number, boolean 등 원본 타입 유지 |
| 형식 지정 타입 | string(date-time), string(date), string(uri) 등 명세에 정의된 형식 표시 |
| 객체 | object 및 참조 Schema 또는 하위 속성 설명 |
| 배열 | array 및 `items`의 타입·참조 모델 설명 |
| 참조 모델 | `$ref`가 가리키는 실제 Schema명 기록 |
| 열거형 | 원본 Enum 값 전체 및 의미 설명 |
| 조합 모델 | allOf, oneOf, anyOf 등 원본 조합 방식 기록 |
| 타입 미확정 | 원본 명세에 타입이 명시되지 않은 경우 미확인으로 표시 |

#### 4.4 예시 작성 규칙

- 공식 JSON 예제가 있으면 해당 값을 우선 사용한다.
- 공식 예제가 없으면 타입, 형식 및 업무 의미에 맞는 예시를 제시할 수 있다.
- 가상 데이터는 `가상 예시`로 구분한다.
- 식별자, URL, 날짜, 금액, 상태값 및 코드값은 해당 속성의 형식과 제약조건에 맞게 작성한다.
- 실제 표준 Enum 값이 존재하면 임의의 값으로 대체하지 않는다.
- 예시가 적절하지 않거나 근거가 없는 경우 임의로 만들지 않고 `예시 미확인`으로 표시한다.

### 5. API 인터페이스 규격

#### 5.1 Operation별 인터페이스 요약

| 기능 | Method | Endpoint | Operation ID | 성공 응답 | 비고 |
|---|---|---|---|---|---|
| 명세 기반 기능 | 정의된 Method | 정의된 Path | 정의된 ID | 정의된 응답 코드·모델 | 조건 및 참고사항 |

#### 5.2 요청·응답 상세 규격

각 Operation별로 다음 항목을 분석한다.

- 요청 목적 및 처리 기능
- Path Parameter
- Query Parameter
- Header Parameter
- Request Body
- Response Code
- Response Header
- Response Body
- 오류 응답 및 관련 공통 모델

요청 또는 응답이 없는 Operation은 해당 명세를 기준으로 설명한다.

#### 5.3 파라미터 상세 표

| 구분 | 파라미터 | 타입 | 필수 | 예시 | 설명 |
|---|---|---|---|---|---|
| Path / Query / Header / Body | 명세상 이름 | 원본 타입 | 필수·선택 여부 | 공식 또는 가상 예시 | 기능과 제약조건 |

필수 여부는 OAS의 `required` 정의를 기준으로 작성한다. Request Body 내부 속성의 필수 여부와 파라미터 자체의 필수 여부를 혼동하지 않는다.

### 6. JSON 요청·응답 예시

- 주요 Operation별 Request JSON
- 성공 Response JSON
- 오류 Response JSON
- 중첩 객체 및 배열 예시
- 공통 속성과 확장 속성 적용 예시

예시는 실제 Schema의 타입, 필수 속성, Enum 및 제약조건과 일치해야 한다. 공식 예제와 분석자가 작성한 가상 예제를 명확히 구분한다.

### 7. 상태 및 Lifecycle 분석

대상 API에 상태 속성 또는 Lifecycle 정의가 있는 경우 작성한다.

| 모델 / Resource | 상태 속성 | 허용 상태값 | 전이 조건 | 근거 |
|---|---|---|---|---|
| 실제 모델명 | 실제 속성명 | 명세상 Enum | 공식 자료에서 확인된 조건 | Schema 또는 공식 문서 |

- `state` 속성의 존재 여부를 먼저 확인한다.
- 상태값과 상태 전이 규칙을 구분한다.
- Enum 정의만으로 상태 전이 순서를 임의 추론하지 않는다.
- 전이 규칙이 공식 자료에 없는 경우 `전이 규칙 미확인`으로 표시한다.
- 상태 속성이 없는 API에는 상태 전이 표를 억지로 생성하지 않고 `해당 버전 명세에서 별도 상태 속성 미확인` 등으로 기록한다.

### 8. 이벤트 및 알림 규격

이벤트, Notification, Hub 또는 Callback 기능이 정의된 경우 작성한다.

| 이벤트명 | 발생 조건 | Payload 모델 | 주요 속성 | 구독·전달 방식 | 근거 |
|---|---|---|---|---|---|
| 공식 이벤트명 | 공식 정의 또는 미확인 | 정의된 모델 | 주요 속성 | OAS 정의 기준 | 근거 위치 |

- 이벤트명과 Payload Schema를 공식 명세 기준으로 작성한다.
- 이벤트 생성 조건이 공식 자료에 없으면 추정하여 확정하지 않는다.
- Hub 등록·해제 및 Callback 인터페이스는 실제 정의된 경우에만 분석한다.
- 이벤트가 없는 경우 해당 API 명세에서 이벤트·알림 기능을 확인할 수 없다고 기록한다.

### 9. 오류 및 예외 처리

- HTTP 응답 코드
- 오류 응답 Schema
- 오류 코드 및 메시지
- 필드 검증 오류
- 권한·인증 관련 응답(명세에 정의된 경우)
- 재시도 또는 복구 관련 공식 지침(존재하는 경우)

OAS에 정의된 응답 코드와 오류 모델을 우선 작성한다. User Guide 등 보조 자료에만 존재하는 오류 처리 지침은 출처를 구분한다.

### 10. 관련 표준 및 연관 API

- 관련 TM Forum Open API
- 공통 데이터 모델 및 관련 Resource
- API 간 연계 관계
- 표준 참조 자료 및 공식 URL
- 연관 API와의 역할 구분

연관 API는 공식 근거 또는 확인 가능한 업무 관계가 있는 경우에만 제시한다. 단순히 유사한 기능이라는 이유만으로 직접적인 표준 의존 관계로 단정하지 않는다.

### 11. 분석 결과 및 검증 내역

- 주요 기능 요약
- 핵심 Resource와 데이터 모델 요약
- 주요 인터페이스 요약
- 상태·이벤트 지원 여부
- 자료 간 불일치 및 미확인 사항
- 검증 결과 및 추가 확인 필요 항목

## 5. 데이터 모델 전수 분석 및 누락 방지 규칙

### 5.1 분석 대상 집합

원본 OAS에서 다음 대상을 추출하여 분석 목록을 작성한다.

1. `components.schemas` 또는 해당 버전에서 사용되는 Schema 정의
2. 각 Operation의 Request Body 및 Response Schema
3. Path, Query, Header Parameter Schema
4. `$ref`로 연결되는 모든 하위 Schema
5. 배열 `items`가 참조하는 Schema
6. `allOf`, `oneOf`, `anyOf`의 구성 Schema
7. 이벤트 및 Notification Payload Schema
8. 공통 모델, 오류 모델 및 실제 사용되는 확장 모델

위 목록은 적용 가능한 OAS 구조에 맞게 사용한다. OAS 버전에 따라 정의 위치가 다르면 해당 버전의 구조를 따른다.

### 5.2 전수 분석 원칙

- Schema 이름만 나열하고 속성 명세를 생략하지 않는다.
- 상위 모델에서 하위 모델을 참조한다는 이유로 하위 속성을 생략하지 않는다.
- 동일 Schema가 여러 Operation에서 사용되더라도 전체 모델 정의는 한 번 완전하게 작성하고, 각 Operation에서 해당 모델을 참조하도록 연결한다.
- 동일 속성이 여러 모델에 별도로 정의되어 있으면 각각의 정의와 제약조건을 확인한다.
- 순환 참조가 있으면 참조 관계를 기록하고 무한 반복 작성은 방지한다.
- 미사용 Schema도 원본 정의 목록에는 기록하고, 실제 인터페이스 사용 여부를 구분한다.

### 5.3 완전성 검증표

| 검증 항목 | 검증 기준 | 결과 |
|---|---|---|
| Operation | 원본 명세와 분석서의 Operation 목록 대조 | 일치 / 누락 / 검토 필요 |
| Schema | 원본 정의와 분석 대상 Schema 목록 대조 | 일치 / 누락 / 검토 필요 |
| 속성 | 각 Schema의 원본 속성 수와 분석서 속성 수 대조 | 일치 / 누락 / 검토 필요 |
| 하위 모델 | `$ref`, 배열, 객체 및 조합 모델의 참조 추적 확인 | 완료 / 미완료 |
| 필수 속성 | required 정의와 분석서 표시 비교 | 일치 / 불일치 |
| Enum·제약조건 | 허용값 및 제약조건 누락 여부 확인 | 일치 / 누락 |
| 요청·응답 | Operation별 Request·Response Schema 대조 | 일치 / 누락 |
| 상태·이벤트 | 관련 정의 존재 여부와 분석서 반영 여부 확인 | 일치 / 해당 없음 / 검토 필요 |
| 예시 | JSON 예시와 Schema의 타입·필수·Enum 검증 | 통과 / 오류 |
| 출처 | 주요 정의의 근거 위치 기록 여부 확인 | 완료 / 미완료 |

수량 비교는 실제 원본 명세에서 추출한 기준 수량을 사용한다. 자동 추출이나 검증을 수행하지 못했다면 검증 완료로 표시하지 않는다.

## 6. API별 차이 처리 규칙

| 구분 | 적용 방법 |
|---|---|
| Resource 중심 API | Resource 구조, CRUD Operation 및 관련 하위 모델을 중심으로 작성 |
| 업무 프로세스 API | 프로세스 모델, 상태, 단계 및 관련 Operation을 명세 범위에서 분석 |
| 카탈로그·상품 API | 상품·오퍼·스펙 등 실제 정의된 모델 및 관계를 분석 |
| 주문 API | 주문 Resource, 항목, 상태 및 관련 이벤트 정의를 확인 |
| 자격·적격성 검증 API | 검증 요청·결과, 조건 및 응답 모델을 명세 기준으로 분석 |
| 이벤트 중심 기능 | 이벤트명, Payload, 구독·전달 인터페이스를 중심으로 작성 |
| 상태 속성이 없는 API | 상태 전이 분석을 해당 없음 또는 미확인으로 구분 |
| 이벤트 기능이 없는 API | 이벤트 규격을 임의 생성하지 않고 미정의 여부를 기록 |
| 버전별 구조 차이가 있는 API | 각 버전의 실제 OAS 구조와 정의를 별도로 분석 |

위 예시는 분석 방향을 설명하기 위한 분류이며, 각 API의 실제 기능과 데이터 모델은 대상 버전의 공식 명세를 기준으로 확정한다.

## 7. 품질 검증 기준

### 7.1 필수 검증

- API ID, API명 및 버전이 대상 명세와 일치하는가?
- Operation, Endpoint 및 Operation ID가 원본과 일치하는가?
- 모든 대상 Schema와 속성이 누락 없이 작성되었는가?
- 하위 모델, 배열 원소 및 참조 Schema가 추적되었는가?
- 타입, 필수 여부, Enum 및 제약조건이 정확한가?
- 요청·응답 및 오류 모델이 Operation별로 연결되었는가?
- 공식 예제와 가상 예시가 구분되었는가?
- 상태 전이와 이벤트 정의가 실제 근거에 기반하는가?
- 자료 간 불일치와 미확인 사항이 기록되었는가?
- 분석서의 수량 검증 결과가 실제 확인 내역과 일치하는가?

### 7.2 검증 결과 표시

- **확정:** 공식 명세 또는 확인 가능한 근거로 검증 완료
- **검토 필요:** 자료 간 불일치 또는 추가 확인 필요
- **근거 미확인:** 확인 가능한 근거 자료가 없음
- **해당 없음:** 대상 API 명세에 적용 가능한 항목이 없음
- **검증 미수행:** 항목은 식별했으나 실제 대조·검증을 수행하지 않음

## 8. 재사용 가능한 AI 작성 프롬프트

다음 프롬프트를 TMF Open API별 분석서 작성에 공통 적용한다.

---

**역할**

당신은 TM Forum Open API 표준 및 인터페이스 설계 전문가다. 제공된 공식 OAS/Swagger와 관련 공식 자료를 기반으로 API별 연동 규격서를 작성한다.

**입력 정보**

- API ID: [예: TMF632]
- API 공식 명칭: [API명]
- API 버전: [버전]
- 분석 대상 자료: [OAS/Swagger, User Guide, Conformance Profile, JSON 예제 등]
- 작성 언어: 한국어
- 작성 목적: 표준 기반 API 분석 및 연동 인터페이스 설계

**작성 지시**

1. 제공된 자료에서 확인되는 사실을 우선 사용하고, 자료에 없는 내용을 공식 정의처럼 작성하지 마라.
2. 대상 API의 공식 ID, 명칭 및 버전을 확인하고 다른 버전의 정의를 혼합하지 마라.
3. 다음 목차를 기준으로 분석서를 작성하라.

   1. API 개요  
   2. 기능 및 Operation 요약  
   3. Resource 및 데이터 모델 구조  
   4. 데이터 모델별 전체 속성 명세  
   5. API 인터페이스 규격  
   6. JSON 요청·응답 예시  
   7. 상태 및 Lifecycle 분석  
   8. 이벤트 및 알림 규격  
   9. 오류 및 예외 처리  
   10. 관련 표준 및 연관 API  
   11. 분석 결과 및 검증 내역

4. 대상 OAS에 정의된 Operation, Schema 및 속성을 전수 조사하라.
5. 모든 주요 데이터 모델과 하위 데이터 모델을 재귀적으로 추적하라. `$ref`, 배열 `items`, 중첩 객체, `allOf`, `oneOf`, `anyOf` 및 실제 상속·조합 관계를 확인하라.
6. 각 데이터 모델의 속성은 **속성 → 타입 → 예시 → 설명** 순서로 작성하라.
7. 필수 여부, Enum, 기본값, 형식, 길이·범위 제약조건 및 읽기·쓰기 제약조건 등 원본에 정의된 정보를 누락하지 마라. 추가 컬럼이 필요하면 기본 컬럼 순서를 유지하면서 보완하라.
8. Operation별 Method, Endpoint, Operation ID, Path·Query·Header Parameter, Request Body, Response Code 및 Response Body를 분석하라.
9. 상태 전이, 이벤트, Notification, Hub, Callback 및 오류 처리 항목은 실제 정의와 근거가 있는 경우에만 상세 작성하라. 없는 항목은 해당 없음 또는 근거 미확인으로 구분하라.
10. 공식 JSON 예제를 우선 사용하고, 직접 작성한 예시는 가상 예시로 명시하라. 타입·필수 속성·Enum 및 제약조건과 일치하는지 확인하라.
11. API명, Resource명, 속성명, Method, Endpoint, Operation ID 및 Enum 값은 원문 표기를 유지하고 설명은 한국어로 작성하라.
12. 각 주요 항목에 근거 자료명, 버전 및 Schema·Operation 등 확인 가능한 위치를 기록하라.
13. 자료가 없거나 정의가 불명확한 경우 임의로 채우지 말고 근거 미확인 또는 검토 필요로 표시하라.
14. 마지막에 원본 명세와 분석서의 Operation·Schema·속성·필수 항목·Enum·제약조건·요청·응답을 대조하고 완전성 검증표를 작성하라.
15. 실제 검증을 수행하지 않은 항목은 검증 완료로 표시하지 마라.

**최종 산출물 기준**

- TMF Open API 연동 규격서로 바로 검토할 수 있는 수준의 상세도
- 원본 표준 명칭과 구조의 보존
- 모든 대상 데이터 모델 및 하위 속성의 누락 방지
- API 버전별 정의 차이의 명확한 구분
- 공식 근거와 분석자 해석의 구분
- 검증 상태와 미확인 사항의 명시

## 9. 최종 적용 기준

본 작성 표준은 모든 TMF Open API 연동 규격서의 공통 기준으로 적용한다. 단, 실제 작성 시에는 대상 API의 공식 명세에 정의된 구조와 기능을 우선하며, 공통 목차 중 적용되지 않는 항목은 임의로 생성하지 않고 해당 없음 또는 근거 미확인으로 구분한다.

연동 규격서의 완료 여부는 문서의 분량이 아니라 **공식 명세 대비 항목의 완전성, 정의의 정확성, 근거의 추적 가능성 및 검증 결과**를 기준으로 판단한다.
